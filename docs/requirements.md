# 新規プロジェクト：社内規則 Q&A チャットボット（ポートフォリオ用デモアプリ）

## 1. 目的
- 架空の会社の社内規則（就業規則・規程類）をもとに、社員の質問に答えるチャットボットを作る。
- ポートフォリオとして公開するデモアプリ。見る人は非エンジニアが中心。
- 見せどころは次の 3 つ。
  - 回答に根拠の条文（規程名・条番号・本文）を必ず添える。
  - 規則に書かれていないことは推測で答えず、「規則には記載がありません」と答える。
  - AI がなくても、検索だけで該当する条文を示せる。
- 名前は仮：リポジトリ `rule-qa-ai`、exe `RuleQA.exe`（決まっていなければ最初に確認する）。

## 2. 方針（既存プロジェクト OrderMail と同じ）
- 無料またはきわめて低価格で作り、外部要素はできるだけ使わない。
- zip を展開して exe を起動するだけで動く（インストール不要・.NET 不要・DB サーバー不要）。
  - Docker・DB サーバー・Node.js・Python を必須にしない。
- C# / .NET 10。画面は exe に内蔵した Blazor Server と Fluent UI Blazor。DB は SQLite（EF Core）。テストは xUnit。
- AI は接続設定式（OpenAI 互換 API）。Azure OpenAI・OpenAI・Gemini・Ollama・LM Studio に対応する。
- AI がなくても動く（検索結果の条文を表示するだけのモード）。
- ロジックは `src/<App>.Core` に置き、画面（`src/<App>.Web`）には置かない。
- 実行中に作るものは、展開したフォルダの `data` の中だけに置く。`%TEMP%` やレジストリなど、フォルダの外にファイルを残さない。
- 返答・コミットメッセージ・PR・ドキュメントは日本語で書く。

## 3. 機能

### 3.1 規則文書の取り込み
- 対象は `.md` と `.txt`。`.docx` と `.pdf` は余力があれば対応する。使うライブラリは MIT か Apache など、配布に支障のないライセンスに限る。
- 初回起動時に、同梱のサンプル規則（`samples/rules`）を自動で取り込む。
- 設定画面からフォルダを指定して取り込み直せる。ファイルの更新日時やハッシュで変わったものだけを処理する。
- 「第○条」「第○章」などの見出しで条文単位に分け、規程名・章・条番号・条見出し・本文を保存する。
  - 条が長すぎるときは項で分ける。条番号を持たない文書は段落で分ける。

### 3.2 検索（RAG の検索部分）
- キーワード検索：日本語に対応した全文検索。SQLite FTS5 の trigram か、OrderMail と同じ文字一致方式を使う。どちらにしても 1〜2 文字の語を扱えるようにする。
- ベクトル検索（任意）：チャットと同じ接続先の `/embeddings` で条文ごとにベクトルを作り、SQLite に保存して全件と比べる。ベクトル DB は使わない。
- 2 つの順位を RRF（Reciprocal Rank Fusion）で合わせ、上位の条文（既定 6 件程度）を候補にする。
- 埋め込みモデルを設定していなければ、キーワード検索だけで動く。

### 3.3 回答
- 候補の条文を「規程名・条番号・本文」の形でプロンプトに付け、次のように指示する。
  - 「候補の条文だけを根拠に答える」
  - 「根拠にした条文の ID を返す」
  - 「根拠がなければ記載なしと答える」
- 出力は JSON（回答文・根拠の条文 ID・回答できたかどうか）にする。
- アプリ側で検証する。
  - 返ってきた条文 ID が候補にないものは消す（作り話の引用を防ぐ）。
  - 根拠が 0 件なら「記載なし」として扱う。
- 画面では、回答の下に根拠の条文を規程名・条番号つきで表示し、展開すると全文を読めるようにする。
- AI なしのモードでは、「該当しそうな条文」として候補をそのまま表示する。
- 会話の続き（「それは試用期間中も同じ？」など）は、直近の数往復を検索とプロンプトに含めて扱う。

### 3.4 フィードバックと評価
- 回答ごとに「役に立った・立たなかった」を記録する。
- 評価用の質問セット（`samples/questions.json`）で次の一致率を出す。各質問には、正解の条文 ID と、記載なしが正解かどうかを持たせる。
  - 検索：正解の条文が候補に入った割合。
  - 回答：根拠の条文が合っている割合、記載なしを正しく答えた割合。
- 設定画面から評価を実行し、プロンプトや検索件数を変えたときの効果を比べられるようにする。

### 3.5 画面（案）
| 画面 | 内容 |
|---|---|
| 質問 | チャット形式。回答と根拠の条文を表示し、フィードバックを受け付ける |
| 規則一覧 | 取り込んだ規程と条文を閲覧・検索する |
| 履歴 | 過去の質問と回答、フィードバックの集計 |
| 設定 | 規則の取り込み、AI の接続先（プリセットとテスト）、埋め込みモデル、プロンプトの編集、試し検索、評価の実行 |

- 起動時に「ポートフォリオ用のデモアプリで、規則は架空のサンプル」という案内をポップアップで出す。ブラウザのタブごとに 1 回だけ表示する。

## 4. サンプルデータ
- 架空の会社の規程を 5〜6 本作る（例：就業規則、休暇規程、旅費規程、経費精算規程、情報セキュリティ規程、在宅勤務規程）。
  - 実在の会社名・人名・実際の規程の文章は使わない。
- 規程のあいだで紛らわしい条文をわざと入れる。検索と回答の選び分けを見せるため。
  - 例：国内出張と海外出張の日当の違い、試用期間中の扱い、申請期限の違い。
- 評価用の質問を 30 問程度用意する。言い換え・あいまいな質問・規則にない質問（記載なしが正解）を含める。

## 5. テストと開発の進め方
- 変更後は `dotnet test` を実行する。ロジックを変えたらテストを足す。
- テストには `[Spec(区分, 項目名, 確認内容)]` を付ける（付いていないとテストが失敗する仕組みも流用する）。
  - テスト仕様書 `docs/test-spec.md` はテストから自動で作るので、手で直さない。
- 規則の分割と検索のロジックを変えたら、評価用の質問セットでの検索正解率を確認する（AI なしで計算できる部分）。
- AI 接続は、偽の HTTP サーバーで送信内容を確かめるテストにする。
- 進め方は、OrderMail の `.cursor/rules` の 3 ファイルをコピーして名前を置き換える。
  - 実装前に計画を出して Go を待つ。
  - コミット前に挙動の確認を依頼する。
  - 1 ブランチ 1 目的で、PR はスカッシュマージ。
- 配布物は `scripts/publish.ps1` で zip にする。確認用に `<App>-latest\<App>.exe` を作り直す（`data` は残す）。

## 7. 最初の進め方
1. リポジトリ名・アプリ名・対応する文書形式を確認する。
2. 骨組みを作る：ソリューション、Core・Web・Tests、開発ルール、CI、publish、デモの案内、AI 接続設定。
3. サンプル規則と評価用の質問セットを作り、分割と検索を AI なしで実装する。検索正解率をテストで出す。
4. 回答の生成、引用の検証、記載なしの判定を作る。
5. 画面（質問、規則一覧、履歴、設定）を作る。
6. 評価画面とフィードバックを作る。
7. ポートフォリオ資料（案内 PDF・README・利用条件・外部部品のライセンス表記）を作る。

各段階は 1 ブランチ 1 PR で進め、計画を出して Go をもらってから実装する。
